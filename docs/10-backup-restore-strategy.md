# Backup and Restore Strategy

This project separates backup responsibilities by data type.

The EKS environment is short-lived for the portfolio demo, but the backup design follows production-style separation of concerns.

## Backup responsibilities

```text
Kubernetes resources  -> Velero -> S3 backup bucket
RDS PostgreSQL data   -> RDS automated backups and manual snapshots
S3 documents          -> S3 versioning and lifecycle protection
Terraform state       -> S3 backend with locking
OpenSearch demo data  -> Rebuild from application logs, optional snapshot later
```

## Velero

Velero stores Kubernetes backups in a dedicated S3 bucket:

```text
church-prod-demo-velero-backups-302530480617-us-east-1
```

Velero backs up Kubernetes objects such as:

- Namespaces
- Deployments
- Services
- ConfigMaps
- Secrets
- Ingress resources
- ServiceAccounts
- RBAC objects
- PVC definitions
- Argo CD applications
- Monitoring and logging Kubernetes manifests

Velero does not replace RDS backups. Database data remains backed up through RDS snapshots and automated backups.

## Velero IAM access

Velero uses IRSA with this service account:

```text
system:serviceaccount:velero:velero
```

The Terraform module creates:

- S3 bucket for Velero backups
- IAM role for Velero
- IAM policy for S3 backup access
- EC2 snapshot permissions for EBS volume snapshots

## RDS backup strategy

RDS PostgreSQL protects application database data:

```text
auth_db
church_core_db
document_core_db
```

Planned protection:

- Automated backups enabled
- Point-in-time recovery through RDS backup retention
- Manual snapshot before destroy or risky changes
- Restore to a new RDS instance if needed

Before destroying the demo environment, create a final manual snapshot if the database contains useful demo data.

Example:

```bash
aws rds create-db-snapshot \
  --db-instance-identifier church-prod-demo-postgres \
  --db-snapshot-identifier church-prod-demo-postgres-final-$(date +%Y%m%d%H%M)
```

## S3 document backup strategy

The document service stores uploaded files in the S3 document bucket.

Protection:

- Versioning enabled
- Public access blocked
- Server-side encryption enabled
- Lifecycle cleanup for old noncurrent versions

For the demo, the document bucket is destroyable by Terraform because this is a short-lived environment. For real production, `force_destroy` should be false.

## OpenSearch backup strategy

For the short-lived demo, OpenSearch is not treated as a system of record.

Logs can be regenerated by:

- Redeploying the application
- Sending test traffic
- Reviewing new Fluent Bit logs in OpenSearch Dashboards

For real production, OpenSearch should use snapshot repositories and retention policies.

## Terraform state recovery

Terraform state is stored in the backend S3 bucket:

```text
emmauopeople-k8s-microservice-cms-tfstate-prod-demo
```

Protection:

- S3 backend
- Encryption
- Locking
- Versioning should remain enabled on the backend bucket

Never delete the backend bucket while resources still exist.

## Apply-day backup order

After the platform is running and before testing destructive changes:

1. Confirm RDS automated backups are enabled.
2. Create a manual RDS snapshot if useful data exists.
3. Confirm the S3 document bucket has versioning enabled.
4. Confirm Velero backup storage location is available.
5. Run an on-demand Velero backup.
6. Confirm the backup completed successfully.

Example Velero backup:

```bash
velero backup create pre-demo-change-$(date +%Y%m%d%H%M) \
  --include-namespaces church-prod,monitoring,logging,argocd
```

Check status:

```bash
velero backup get
velero backup describe <backup-name>
```

## Restore examples

Restore Kubernetes resources from Velero:

```bash
velero restore create restore-from-pre-demo-change \
  --from-backup <backup-name>
```

Restore RDS from snapshot:

```bash
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier church-prod-demo-postgres-restore \
  --db-snapshot-identifier <snapshot-id>
```

Restore a previous S3 document object version:

```bash
aws s3api list-object-versions \
  --bucket <document-bucket-name> \
  --prefix <object-key>
```

Then copy the required version back to the current key.

## Destroy-day checklist

Before `terraform destroy`:

1. Capture required screenshots.
2. Export Grafana dashboard screenshots.
3. Export OpenSearch Dashboards screenshots.
4. Create final RDS snapshot if needed.
5. Confirm S3 document bucket content is no longer needed.
6. Confirm Velero backup bucket content is no longer needed.
7. Run `terraform plan -destroy` and review carefully.
8. Destroy only when ready.

## What Velero does not protect

Velero should not be treated as the only backup for:

- RDS database contents
- S3 document objects
- Terraform state
- ECR images
- Git repository contents

Those resources have separate backup or recovery paths.
